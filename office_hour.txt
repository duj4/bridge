Good afternoon, everyone. Thanks for having me.

Today, I’d like to walk you through SecArch Tickets, an application that brings security architecture requests into one place and makes them easier to track.

The goal is straightforward: help people quickly understand what’s open, which systems and departments are involved, and what needs attention next.

For requesters, that means clearer visibility into their requests. For the SecArch team, it means an easier way to review the queue, capture progress, and prepare updates for stakeholders.

[Show the main dashboard.]

The application pulls the supported security review and exception requests through the CMDB APIs and enriches them with system ownership information.

One key design choice is that department ownership comes from CMDB. That gives us a consistent way to organize requests around the teams responsible for the systems involved.

The existing ITSM ticket remains the reference for the underlying request, and each ticket number links directly back to it.

Let me show you how that works in practice.

The page opens with the active queue. At the top, we can see the total number of tickets and how many are still open.

Each row brings together the essential information: the ticket summary, the system, the department, the reporter, the assignee, and the expected date.

[Select a department, then demonstrate search.]

I can narrow the view to one or more departments, or search by ticket number, summary, system, or owner. I can also switch between open and closed tickets and sort the table.

That makes the same page useful for a quick individual lookup, a departmental review, or a broader discussion of the workload.

[Open an existing open ticket.]

Inside a ticket, we can see the details alongside two features for day-to-day coordination: an expected date and a history of progress updates.

The expected date gives us a visible planning reference. In the main table, dates approaching within seven days are highlighted, and overdue dates are clearly marked. That helps us identify where follow-up may be needed.

We can also add a short update—for example, that we’re waiting for an architecture document, or that a follow-up review has been scheduled.

Each update is timestamped, so the next person can pick up the context.

These dates and notes are stored locally in SecArch Tickets. They remain available across synchronizations and are kept separate from the source ticket data. Changes here stay within the application; they aren’t written back to ITSM.

[Close the details and open Export XLSX.]

For reporting, we can export closed tickets over a selected date range, using a preset or custom dates.

The Excel workbook creates a separate worksheet for each department. That makes it easier to share completed work with stakeholders and prepare for periodic reviews.

Another design priority is reliability.

The application uses a Go service backed by PostgreSQL, which stores a durable snapshot of the ticket data. When we open the page, it shows that stored data first, then requests a synchronization when the shared waiting period allows.

If synchronization fails, the existing data remains available. The interface shows the synchronization status and last successful sync time, so users can judge how current the information is.

Finally, a quick note on access control. The OIDC integration is implemented, but it hasn’t been deployed yet.

Once enabled, administrators will have access to all tickets, while other users will only be able to access tickets they reported. Those checks are enforced by the backend across ticket views, updates, and reporting.

The overall benefit is a clearer view of security review work, with less effort spent finding context and preparing status updates.
