**Subject: JSM MCP Integration – OAuth Delegated Authentication and HTTP Header Configuration API**

Hi Kantega Support Team,

We are evaluating two authentication approaches for an internal AI/MCP integration with Jira Service Management Data Center and would appreciate your guidance on the supported options.

**Environment:**
- JSM Data Center 11.3.x
- Kantega SSO Enterprise 8.11.6p7
- Microsoft Entra ID (Azure AD China) as our existing OIDC Identity Provider

**Proposed Integration:**

1. A local Windsurf MCP server authenticates to our internal `cmdb-api-server` using Kerberos/SPNEGO with a dedicated AI account (e.g., `dujas_ai`).
2. `cmdb-api-server` validates the AI identity and maps it to the corresponding human user (`dujas_ai → dujas`). This mapping is managed entirely within our application.
3. We want subsequent JSM REST API requests to be authenticated as the mapped human user (`dujas`), preserving their existing JSM permissions without requiring a separate licensed JSM account for the AI agent.

We are considering the following two options.

### Option 1 – OAuth 2.0 Authentication

We are interested in Kantega's OAuth 2.0 Resource Server functionality as an alternative to HTTP Header Authentication.

Our preference would be a service-to-service authentication mechanism that does not require each human user to perform an additional interactive OAuth login or consent process.

Could you please clarify:

1. Can the OAuth Resource Server authenticate a JSM REST API request as an existing human user when the calling application has already authenticated and mapped the AI identity to that user?

2. Is there a supported approach using OAuth Client Credentials, administrator pre-consent, Token Exchange, or another delegated authentication mechanism that would allow `cmdb-api-server` to obtain an authorized token representing the mapped human user without requiring individual interactive authorization?

3. If a user-delegated Access Token is mandatory, would each human user need to complete an initial OAuth login or authorization process? Could subsequent requests operate without further user interaction?

4. Does the Resource Server support an application-level identity assertion or a verified custom claim for resolving the effective Jira user? If so, how is the application prevented from impersonating unauthorized users?

We understand that mapping `dujas_ai` to `dujas` within our application does not, by itself, constitute OAuth authorization. We would appreciate your recommendation for a supported and secure implementation.

### Option 2 – HTTP Header Authentication Enhancement

We have already successfully validated HTTP Header Authentication in our QA environment. By sending a custom header such as:

`X-MCP-PoC-User: dujas`

Kantega authenticated the JSM REST API request as `dujas`. Requests with an invalid username or without the header returned HTTP 401.

However, our existing Layer 4 and proposed Layer 7 F5 virtual servers may share the same server-side source IP, making IP-based isolation challenging.

We are exploring whether additional controls could improve this approach.

Specifically:

1. Does Kantega provide a supported REST API to programmatically update the **HTTP Username Header Name** (the header key, not its value)?

2. If supported, could we periodically rotate the configured header name and synchronize it with `cmdb-api-server` without modifying the configuration manually?

3. Would such changes take effect across all JSM Data Center cluster nodes without requiring a restart? Is there any risk of temporarily disrupting existing authentication methods?

4. If no dedicated configuration API exists, is there another supported mechanism for securely validating a trusted identity assertion, such as a signed header or token, without relying solely on the HTTP header name and source IP?

We understand that rotating or obscuring the header name alone would not provide strong authentication, so we are also interested in any additional security controls Kantega would recommend.

### Our Goal

Ideally, we would like to retain Kerberos authentication between the local MCP server and `cmdb-api-server`, while finding a secure, supported way for JSM to authenticate REST requests as the mapped human user.

We would also prefer to minimize changes to our existing JSM load-balancing infrastructure and avoid developing a custom JSM authentication plugin.

Could you advise which approach you would recommend, along with the required Kantega version and any relevant configuration documentation?

Thanks in advance for your guidance.
